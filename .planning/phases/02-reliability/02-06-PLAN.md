<objective>
One run per head unless the owner forces another: deduplication at job start (REL-04), attachment to an active job in one transaction and `--force` (REL-11), a waiting review that follows its job's state and stops cleanly on Ctrl-C, and the REL-05 check with a real previous run.

Purpose: SPEC "Job" (deduplication against finished work at job start), "One model for every process" (attach rules, waiting, Ctrl-C output), "Commands" (`review <pr-url> [--force]`); ROADMAP criteria 4, 5 and 11.
Output: `--force`, the attach transaction, reuse at job start, stored-result printing, the wait loop, and black-box plus property tests.
</objective>

<assumption_delta_decision>
Primary noun: the review job (with the run it produces). Decision: no-change. Job and run identities stay surrogate row IDs; neither (target) nor (target, head, forced) can be a unique key, because REL-11's forced second run and SPEC's "a new run never overwrites an earlier one" need several runs per (target, head) and up to two active review jobs per target (one running, one queued). The attach key (active review job of the target, queued first) and the reuse key (succeeded run with the same target and head, job not forced) are lookups inside the transaction, and force and origin are attributes added in plan 02-01. The "also" signal from the planning note is noise. Invariant test that encodes the intent: Task 3's proptest that enqueue never creates a review job while the target has a queued one and that a non-forced request never creates a job while any job of the target is active.
</assumption_delta_decision>

## Flagged assumptions

- REL-04 edge: "same head" means the head SHA resolved at job start (from the fetched pull ref) equals the head_sha of a succeeded run of the same target; the merge-base is not compared, so a base branch move alone still reuses (SPEC: "A base branch change alone never queues a run").
- REL-04 edge: the reuse is reported on stderr only; stdout is the stored draft exactly as the original run printed it.
- REL-05 edge: an invalid previous_finding_id is any value not among previous.json's IDs, including a real finding ID of another target or of an older run that is not the latest successful one.
- REL-11 edge: among active jobs a request attaches to the queued one first, so a request started while a re-run is queued joins the re-run, as SPEC's "a review started while a tui re-run is queued attaches to it" requires even when another job is running.
- REL-11 edge: a waiting review also prints its job's result when another runner finished it while it waited; this is SPEC's "It then waits for the job it attached to or created" and is what QUE-09 (Phase 3) will verify with `watch`.
- REL-11 edge: "Stopped waiting" exits with code 1, as Phase 1 D-04 has no code for a stopped wait.
